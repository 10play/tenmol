# @tenmol/graph — PyMOL feature knowledge graph

A structured catalog of **every user-facing feature of PyMOL**, built for the tenmol parity port.
It has two tiers:

1. **A generic manifest** — one row per feature, machine-readable (`manifest.json`) and human-readable
   (`MANIFEST.md`). **1,643 features** across commands, settings, colors, representations, the
   selection language, wizards, presets, and UI.
2. **Per-feature deep-dive docs** — under `features/`, one Markdown file (or `##` section) per feature
   with purpose, exact syntax/params, behaviour & gotchas, examples, related features, and a source
   ref back into upstream PyMOL.

## Layout

```
packages/graph/
├─ MANIFEST.md            the generic manifest — every feature, grouped by category (generated)
├─ manifest.json          the same data, machine-readable (generated)
├─ index.md               navigation into the deep-dive docs
├─ features/
│  ├─ commands/           one deep-dive .md per cmd.* command (424 files) + _batch-*.manifest.json
│  ├─ settings/           the 779 settings, grouped by prefix family, in 4 batch docs
│  └─ topics/             feature-domain deep dives (representations, selection-algebra, wizards,
│                         presets, movies-scenes-states, maps-volumes, editing-building,
│                         sculpting-minimization, symmetry, fitting-alignment, rendering-export,
│                         file-formats, coloring-system, named-colors, querying-properties,
│                         viewing-camera, ui-main-internal, ui-input-dialogs)
└─ scripts/
   └─ assemble-manifest.mjs   merges every features/**/*.manifest.json sidecar → manifest.json + MANIFEST.md
```

Each doc directory also carries `*.manifest.json` **sidecars**: the structured rows for the features
that doc covers. `manifest.json` / `MANIFEST.md` are assembled purely by merging those sidecars, so
the deep-dive docs are the single source of truth.

## Ground truth

Every entry is grounded in the repo's own **introspected** references (taken from a live PyMOL) plus
the upstream engine source — not from memory or the wiki:

- `docs/api-reference/commands.mdx` — 424 `cmd.*` commands with exact signatures, params, defaults, docstrings
- `docs/api-reference/settings.mdx` — 779 setting names
- `docs/api-reference/colors.mdx` — 178 named colors (RGB from `packages/engine/layer1/Color.cpp`)
- `docs/feature-parity.md` + the 12 per-area docs in `docs/` — feature prose & source refs
- `packages/engine/modules/pymol/*.py` — upstream implementations & docstrings
- `packages/engine-ts/src/**` — the TypeScript parity port (drives `parityStatus`)

Signatures and defaults are copied verbatim from the introspected refs; the wiki
(<https://pymolwiki.org>) was consulted only for clarifying prose.

## Regenerating the manifest

The manifest is derived, never hand-edited. After editing any deep-dive doc or its sidecar:

```sh
pnpm --filter @tenmol/graph build:manifest
# or:  node packages/graph/scripts/assemble-manifest.mjs
```

The script reports sidecar count, rows read, deduped total, per-kind breakdown, and any malformed
sidecars (it exits clean when there are none).

## How it was built

Generated by a multi-agent workflow (`scripts/feature-graph.workflow.js` in the session scratchpad):
43 feature batches, each run through **expand** (a gatherer writes the docs + sidecar) → **verify**
(an independent verifier re-derives the ground-truth item list, checks every signature/default, and
fixes errors in place). 1,115 docs checked, 36 fidelity fixes applied, 0 invalid sidecars.

Each row's `parityStatus` (`implemented` / `partial` / `planned` / `internal` / `unknown`) reflects
whether the feature is present in `packages/engine-ts` and how `docs/feature-parity.md` marks it —
so this doubles as a parity gap map.
