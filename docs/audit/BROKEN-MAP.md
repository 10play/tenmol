# tenmol web-app — UI audit: map of what does not work

Generated by the deterministic UI audit (`scripts/audit/`). Every interactive affordance in `apps/web` was enumerated from source (one reader per feature directory in the frozen registry — nothing sampled), turned into an executable TestSpec, driven on an isolated local-engine browser stack, and every failure was independently re-verified on a fresh stack to eliminate false positives.

## Headline

- **1928** affordances enumerated across **25** areas.
- **582** pass · **409** blocked (untestable in this sandbox — see below) · **937** raw failures before verification.
- Raw failures are dominated by over-strict spec checks. Adversarial re-verification confirmed **11 real defects** out of 300 verified candidates — a ~96% false-positive rejection rate, which is the whole point of the verify layer.
- The 11 confirmed defects collapse to **4 distinct root causes** (7 of them are one Builder-dock bug hitting different controls).
- **70** actionable low-signal candidates (mostly `mouse`/`shortcuts`, many "undrivable by design") plus 7 runner-timeout markers were NOT re-verified before the sandbox hit its PID limit — listed in the appendix, not counted as defects.

## The 4 confirmed defects

### 1. `bg_color` never repaints the live viewport

- **Severity:** 🟠 major · **Area:** `viewport`
- **Symptom:** `bg_color white` runs without error but the live WebGL viewport never repaints — background stays black.
- **Repro:** 1) Load scene, `as cartoon`. 2) Run `bg_color white`. 3) Observe interactive viewport: backdrop remains black instead of turning white (command echoed, no error). Independently reproduced via scripts/audit/run-shard.mjs on /tmp/verify-viewport_render_bgColor.json → FAIL "viewport unchanged".
- **Evidence / root cause:** Fresh screenshot /tmp/vshots/viewport.render.bgColor.png shows black background after `bg_color white` (console shows the command, no console/page errors). Root cause: viewport renderer has setBackground (packages/viewport/src/modeG/renderer.ts:178-181,292-294; viewport.ts:854-855) but the web app never wires the bg_rgb setting to it — background is only ever initialized to null (viewport.ts:195); no bg_rgb→setBackground subscription exists in apps/web/src. Ray path honors bg_rgb (engine-ts/src/cmd/render.ts:42-48,95), so only the interactive canvas is affected.

### 2. Movie frame scrollbar is permanently disabled

- **Severity:** 🟠 major · **Area:** `movie`
- **Symptom:** Frame scrollbar (range input) stays permanently disabled on the local engine because get_movie_status is a stub that always reports nframes:0, even after mset defines a movie.
- **Repro:** 1) Open the app with ?backend=local. 2) In the movie panel run `mset 1 x30` to define a 30-frame movie. 3) Observe the readout still says "FRAME 1/0 · no movie" and the .mvpanel__range input remains disabled (max=1), so the frame scrollbar cannot be moved. Engine-internally cmd.count_frames returns 30 but cmd.get_movie_status still returns nframes:0.
- **Evidence / root cause:** Independent reproduction via the audit harness (?backend=local). After setup `mset 1 x30`: cmd.count_frames=30 and cmd.get_movie_length=30 (movie genuinely created), but cmd.get_movie_status returned {frame:1,nframes:0,...}. Panel showed "FRAME 1/0 · no movie — define one with mset below" and the range element was <input min=1 max=1 disabled value=1>, so Playwright locator.fill times out. Root cause: packages/engine-ts/src/engine.ts:986 registers get_movie_status as a fixed stub returning nframes:0; registerSystem in packages/engine-ts/src/cmd/system.ts overrides get_frame/count_frames/get_movie_length but NOT get_movie_status. apps/web/src/features/movie/movieSource.ts status() calls cmd.get_movie_status first (ensure() succeeds since the stub does not throw) and only falls back to count_frames if it throws, so MoviePanel.tsx:179 keeps the range disabled (nframes<1) forever. The disabled state is the real bug, not a check/timing artifact.

### 3. Scene ▸ Blank throws "No scenes" instead of clearing the view

- **Severity:** 🟠 major · **Area:** `scenes`
- **Symptom:** Scene menu ▸ Blank fails to clear the viewport — it throws "CmdException: No scenes" and leaves the molecule fully rendered instead of disabling all objects.
- **Repro:** 1. Load default session (backend tenmol-engine-ts). 2. Open the Scene panel; click the "Blank" button (.scmenu .scmenu__row button, nth 12), which runs cmd.scene("", "recall"). 3. Observe: the molecule stays fully rendered (viewport unchanged) and the output log shows red "CmdException: No scenes". Expected: screen goes blank (all objects disabled, message cleared).
- **Evidence / root cause:** Fresh shard run (/tmp/verify-scmenu_blank.out.json) → FAIL screenshotChanged "viewport unchanged". Fresh screenshot /tmp/vshots/scmenu.blank.png: cartoon still fully rendered; output panel shows cmd.scene("", "recall") followed by "CmdException: No scenes"; SCENES 0, current: (none). This is not a check/timing artifact — the control genuinely errored and did nothing. Frontend maps Blank → sceneActions.blank() = scene(['','recall']) (apps/web/src/features/scenes/sceneActions.ts:82; SceneMenu.tsx:70), whose own comment says recall '' should "disable all + clear the message". Reference PyMOL engine MovieScene.cpp:794-806 handles empty-key recall via ExecutiveSetObjVisib(G,"*",false,false) (blank screen) and only raises "No scenes" (MovieScene.cpp:783,839) for next/previous/start — so the engine-ts backend wrongly hits the No-scenes path for empty-key recall. Note: the prior audit screenshot (21 scenes) also showed the viewport not blanking, so the affordance is broken regardless of scene count.

### 4. Builder dock does not open on first click (7 controls unreachable)

- **Severity:** 🟠 major · **Area:** `builder`
- **Symptom:** Clicking the "Builder" quick button opens the panel slot but the Builder dock window fails to render on cold load, so the Triple-bond control is unreachable.
- **Repro:** One-spec shard at /tmp/verify-builder_bonds_order_triple.json fails 3/3: "TimeoutError: page.waitForSelector: Timeout 6000ms exceeded — waiting for [data-testid=builder-window]", at the setup step (before builder_dismiss), with zero console/page errors — refuting the reported Clear-modal cascade. Live-browser proof: after the click builder-window is absent, but window.dispatchEvent(new Event('tenmol:open-builder')) makes builder-window and the triple-bond .bbtn appear instantly. Root cause: apps/web/src/shell/FeatureSlot.tsx mounts <MountMarker> before <Panel/> in the same Suspense; MountMarker's useEffect calls panelMounted() (apps/web/src/shell/panelHooks.ts) and dispatches tenmol:open-builder before BuilderPanel's addEventListener runs (apps/web/src/features/builder/BuilderPanel.tsx:112-114), so the open-intent is lost.
- **Evidence / root cause:** Deterministic audit FAIL (3 runs) in isolation with no Clear modal; live-browser confirmation that the panel mounts but never opens until the open event is re-dispatched; effect-ordering race in FeatureSlot.tsx / panelHooks.ts / BuilderPanel.tsx:112-114.
- **Affected controls (same root cause):** `builder.bonds.order.triple`, `builder.model.rest`, `builder.model.sculpt`, `builder.bonds.delete`, `builder.settings.bumps`, `builder.atoms.clear.confirm`, `builder.wizard.cancel`, `builder.wizard.dismiss`

## Blocked / untestable in this sandbox

**409** specs could not be exercised here and are NOT counted as passing. The audit runs against the in-browser TypeScript engine (`?backend=local`), which is the app's default backend. Three capability classes are absent in this sandbox:

- **`remote-backend`** — the WebSocket PyMOL bridge was not booted. Anything that needs the real C++/Python engine (server-side file I/O, some maps/volumes, alignment export) is blocked. This is also why the app shows "file service unavailable" — the server file-service is a remote-backend feature.
- **`bridge-gl`** — no offscreen GL on the bridge, so Mode-P pixel rendering, `ray`, and backend atom picking cannot be tested.
- **`file-service`** — no server filesystem, so `load <path>` fails ("the browser has no filesystem"); only `fetch <pdbid>` and drag-drop file contents work in local mode.

The heaviest blocked areas: `files` (153), `settings` (62), `volume` (43), `seqview` (36).

## How to re-run the audit

The audit is deterministic and re-runnable. Artifacts:

- `scripts/audit/schema.md` — the TestSpec grammar.
- `scripts/audit/driver.mjs` + `run-shard.mjs` — the executor (boots an isolated vite+browser stack per shard on free ports; safe to parallelize).
- `docs/audit/specs/*.json` — the enumerated test map (one file per area, the durable coverage contract).
- `docs/audit/results/*.json` — per-spec verdicts + evidence. `docs/audit/shots/` — a screenshot per spec.
- `scripts/audit/ui-audit.workflow.mjs` — the full 5-phase agent workflow (inventory → execute → adversarial verify → synthesize).

Run one area: `node scripts/audit/run-shard.mjs docs/audit/specs/<area>.json /tmp/out.json /tmp/shots`.
